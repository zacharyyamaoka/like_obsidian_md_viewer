Defect 1 — the architecture forbids block widgets

Why the table isn't 'not done yet'.

The whole live preview is a single ViewPlugin (542 lines, ViewPlugin.fromClass present: True, StateField present: False). CodeMirror forbids a view plugin from producing a decoration that spans a line break. Straight from the installed package:

throw new RangeError("Decorations that replace line breaks may not be specified via plugins");

A GFM table is always at least two lines. So the missing table is not an unimplemented feature — this architecture structurally cannot render one, nor block math, nor a real callout block, nor an embed. SystemSketch hit this for real and had to write its table as a separate StateField to get around it.

Every good implementation already knows this. SilverBullet builds its live preview out of decoratorStateField. Zettlr splits deliberately into renderInlineWidgets (a ViewPlugin, viewport-scoped) and renderBlockWidgets (a StateField, whole-document) for exactly this reason. That split is the architecture to adopt.

Defect 2 — the reveal rule is wrong, and it's the thing that feels off

The measured reason it doesn't feel like Obsidian.

Obsidian's rule is not per-line. Block markers (heading #, list bullet, blockquote >) reveal for their line; inline marks reveal only their own span. Clank reveals everything on the cursor's line at once, because it computes a whole-line active range.

Measured, cursor placed inside **bold**:

Line with **bold** and *italic* and `code` all together.
           ^^^^^^ cursor here

asterisks visible : 6      (Obsidian would show 2)
backticks visible : 2      (Obsidian would show 0)

Every mark on the line pops open at once. That is the "nitty-gritty" wrongness — it reads as the line unravelling rather than one word opening for editing.

Three independent implementations converge on the fix, which is the strongest signal in the whole sweep. SilverBullet checks the cursor against the node's own range (isCursorInRange(state, [from, to])). Zettlr does the same through one shared rangeInSelection helper. Lumina-Note splits explicitly: block marks keyed on the active line, inline marks on shouldShowSource(state, node.from, node.to).

All three also suppress reveal while the mouse is dragging — SilverBullet skips select.pointer transactions, Lumina-Note keeps a mouseSelectingField, atomic-editor freezes decorations between pointerdown and a 100 ms tail after pointerup. Nobody arrives at that by accident; it is what stops text shifting under a click.

A correction worth recording: I initially suspected the missing EditorView.atomicRanges (absent from both codebases) was the cause. I measured it — 0 dead arrow presses in 30 — and CodeMirror's own author says on the CM6 forum that atomicRanges is the wrong tool here, because it makes the whole span move and delete as one unit. Withdrawn.

Defect 3 — a one-line parser bug

Cheapest fix in the report.

Clank calls markdown({ codeLanguages: languages }). It passes no base, and the installed source defaults base to commonmarkLanguage. The GFM-bearing export is markdownLanguage. Run through the real parser:

markdown()                           Table --   Task --   Strikethrough --
markdown({ base: markdownLanguage })  Table YES  Task YES  Strikethrough YES

The parser never emitted a Table node at all. This is also why livePreview.ts hand-rolls regex for ~~strike~~ and task lists — the nodes it would otherwise match do not exist. One line unlocks the parse and deletes that regex.

The port to the card is real, not theoretical

Proven with a running editor, not with a dependency graph.

The plan has always been "make it great standalone, then port it into the canvas card." That only works if the editor is free of framework entanglement. I unpacked the published tarball and checked: only the React wrapper imports React; every extension module is plain CM6.

Then I proved it rather than asserting it — an EditorView assembled by hand from the extension factories, no React anywhere in the graph:

{"tables": 1, "cells": 4, "checkboxes": 2, "reactOnPage": false}

Worth knowing before you plan the order of work: SystemSketch is currently ahead of Clank, not behind. The card already has a real <table> widget and real <img> rendering; Clank has neither. "Build in Clank, port to the card" needs inverting at the start.

What Obsidian actually does

The acceptance criteria, and the places it says build less.

The behavioural spec is the acceptance criteria — without it, "good" is a guess. The findings that change what we would have built:

  • Tables are the whole ballgame. Obsidian shipped a real in-place table editor in 1.5 (Dec 2023): a genuine <table>, editable cells, hover add-controls, right-click alignment, drag-to-reorder. The "clean vs IDE" feeling you described is almost entirely this.
  • Bold marks do not collapse the instant you close them. They stay visible while the cursor touches the span. Collapsing eagerly, Notion-style, would be wrong.
  • Slash commands are not a Notion block menu. Obsidian's / is a core plugin that filters the Command Palette. The Notion-style curated insert menu people picture is a community plugin. Worth deciding which one you actually want — they are different products.
  • %% comments %% are never hidden in Obsidian, cursor or not. Clank hides them. That is a deliberate divergence to keep or drop on purpose.
  • Footnotes don't render in Live Preview in Obsidian either — an acknowledged gap in its own issue tracker. Permission not to over-build.
  • Typography is the quiet half. Proportional Inter, not mono; a graduated heading weight ramp (700, 680, 660, 640, 620, 600) rather than uniform bold; content type scales with the user's font size while UI chrome stays fixed. Minimal, the reference "clean" theme, sets --h1-size: 1.125em and h3 at exactly body size. The clean feel is restraint, not a bigger scale.

One thing to confirm: your "what shows when you press the header button" almost certainly describes a formatting toolbar, which is not core Obsidian — it's the Editing Toolbar community plugin. Worth saying which you meant before it gets built.

The critic's two corrections

An independent review of the direction, with the facts in hand.

The direction — atomic-editor as the base, slash commands from SilverBullet, Zettlr-grade tables on top — went to an independent Fable 5.1 reviewer with every verified fact above. It agreed with the shape and corrected two things.

Vendor atomic-editor; do not depend on it

Of the four gaps measured, only math is additive. The !note callout title, the frontmatter mis-parse and the wikilink bracket leak are bugs inside atomic-editor's own decoration builders — and you cannot layer a fix over a decoration another extension already emitted wrong. "Depend and extend" therefore ends in patch-package, across two repos.

The fork risk is smaller than it sounds: the package has zero runtime dependencies, and the hard-won parts — the pointerdown freeze, virtualization, stable line heights — are exactly the parts that will never be touched. What gets modified is decoration-builder code, the shallow layer. So: vendor the plain-CM6 modules, pin the upstream commit, keep the MIT notice, and send the three bugs upstream anyway. Every merged PR shrinks the carried delta.

Use the React wrapper nowhere — not even in Clank. Make the no-React composition the only path and write a thin React wrapper over it. If Clank consumes the component and SystemSketch consumes hand assembly, there are two code paths on day one and "done once" is already false.

Drop the Zettlr table re-derivation

Click-a-cell-to-edit-in-place already works in atomic-editor. What Zettlr's nested sub-EditorView-per-cell buys on top is full CodeMirror semantics inside a cell — multi-cursor, its own history, its own keymaps — which is overkill for a cell holding a phrase. Worse, its scroll-jump workarounds are ones Zettlr's own code admits it does not understand, and they are GPL, so re-deriving them from prose means rediscovering undocumented pain through pain.

What was actually asked for — ergonomic row and column adding — is precisely md-advanced-tables, which is the engine under the Obsidian plugin the reference users already run. The ergonomics are pre-validated in the exact idiom being cloned.

And on "let's just implement a table": no. The markdown text is the table model — the same source-canonical call already made for the SystemSketch block, and the thing that makes the whole editor portable. Decorate the text; never grow a parallel table structure.

The catch worth acting on

There are two implementations to retire, not one. SystemSketch's markdown block is the same lineage as Clank's. If the package is born and only Clank adopts it, the result is three markdown editors. Definition of done: both existing implementations deleted and consuming the package.

The plan

Ordered by how much feel each step buys per unit of work.

  1. Fix the parser, if the current editor stays in daily use during the migration. markdown({ base: markdownLanguage }), then delete the hand-rolled strikethrough and task regex it was compensating for. One line in, a block of code out. If atomic-editor lands quickly instead, this is throwaway — and so is fixing the old plugin's reveal rule. Don't invest past the one-liner.
  2. Create the package first, not last. A real workspace package (bbox-ui is the natural home, given CodeField's precedent) — not a shadcn registry item, whose copy-into-consumer model is exactly wrong for an engine that will receive continuous fixes. A plain-CM6 core entry, and a /react entry for Clank's wrapper.
  3. Vendor atomic-editor's CM6 modules into it and fix the three decoration bugs there. Tables first, since that is the complaint.
  4. Add slash commands — stock CM6 autocompletion() with a / trigger regex, dispatching into Clank's own command registry so plugins can contribute entries. Decide this before building it; it is expensive to retrofit.
  5. Add table operations via md-advanced-tables behind a ~50-line ITextEditor adapter. Check first whether the ops needed tree-shake clean of ebnf; the formula engine is almost certainly not wanted.
  6. Restyle to Obsidian's restraint — every colour, font and size is already a CSS custom property, so this is token work, not a fork.
  7. Delete both old implementations. That is what makes it "done once".

Three invariants to write into the package README

  • One decoration owner per node type. Table rendering, inline preview and a future math extension must never decorate the same range.
  • One reveal rule, as a shared helper every extension imports. The per-span reveal semantics are the feel being bought; a new decorator that invents its own is how a grafted editor starts feeling stitched together.
  • Explicit keymap precedence, decided once: Tab-in-table versus indent, Enter-in-table versus newline.

Licensing

The permissive set is large enough that nothing copyleft needs to be touched:

  • MIT atomic-editor, SilverBullet, md-advanced-tables, latex-suite, dataview, Obsidian Minimal, and most of the Obsidian plugin corpus.
  • Apache-2.0 Lumina-Note, and ixora — which three SilverBullet files (hide_mark.ts, list.ts, util.ts) are forked from and which must keep their attribution header if those files travel.
  • GPL / AGPL / MPL Zettlr, Joplin, Advanced Tables' plugin shell, Editing Toolbar, Excalidraw. Read for technique; never copy. Note the highest-value one is split: the Advanced Tables plugin is GPL, but the engine underneath it is separately MIT.
